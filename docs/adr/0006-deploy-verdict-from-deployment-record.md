# 0006 A deploy's verdict comes from the deployment record, not the container status

Coolify has no "deploy" endpoint: the app calls `POST /applications/{uuid}/start` (deploy) or `/restart`, and both answer only that the request was **queued**. The outcome used to be inferred by polling `GET /applications` and reading the container `status`, converging on "active for at least 8 seconds".

That cannot work, and it failed in the most damaging direction: **it reported broken deploys as successful.** The `status` in the resource listing describes the *running container*, not the deployment. While a build runs — and after it fails — Coolify leaves the previous container up, still reporting `running:healthy`. A successful deploy and a failed one therefore emit an identical status stream, so any judge reading only that stream must call both a success. The 8-second threshold measured nothing but elapsed time; `Application` exposes no container timestamp, image digest or commit to compare against, so no heuristic over that endpoint can close the gap. The symptom only appeared for resources that were already running, which is the normal case for a redeploy — a deploy of a *stopped* app did surface, as a timeout.

The verdict now comes from the deployment itself. `start`/`restart` return a `deployment_uuid` (already present in `StartResponse`/`RestartResponse`, previously discarded); it is retained and `GET /deployments/{uuid}` is polled until its `status` is terminal — `finished`, `failed` or `cancelled-by-user`. `queued` and `in_progress` are not outcomes and keep the action pending, as does any unrecognised future value: an unknown status is not evidence of success.

The decision lives in `lib/deploy-verdict.ts` as a pure `judgeAction`, deliberately **not** inline in the page. The rule previously existed in two hand-synchronised copies inside `app/page.tsx` — a `useCallback` for the batch queue and a `useEffect` for single actions — neither reachable from a test, which is why the defect survived. `scripts/check-deploy-verdict.mjs` now drives both paths against a fake instance and fails if the page stops using the shared judge.

Three narrower rules follow from the same principle — that only positive evidence counts as success:

- **`finished` is necessary but not sufficient.** The job completing does not mean the container survived it, so a deploy whose container then exits or stays `unhealthy` is a failure, not a success. The listing gets a grace window first, so a lagging refetch is not mistaken for a crash.
- **Transitioning is not arrived.** `isResourceActive` counts `starting` and `restarting` as active while `classifyResourceState` calls them `transitioning` — two classifiers of the same string disagreeing. The judge follows the latter. `isResourceActive` keeps its meaning for filters, counters and badges, where "is this thing up" is the right question.
- **Timing out is not failing.** Giving up establishes nothing, so it is reported as an unknown outcome rather than a clean failure, and it no longer cuts a slow build short: single actions get the same 5-minute budget the batch queue always had, instead of 120 s.

Services and Databases keep the container-status path, hardened by the rules above: their endpoints return no deployment handle, so there is nothing more authoritative to consult.

Validated against a live v4 instance (read-only). Across 194 real deployment records the only statuses that occur are `finished` (157), `failed` (35) and `cancelled-by-user` (2) — all three terminal, none unclassified. On the same instance the old container-only rule yields exactly one verdict for all 50 applications, `succeeded`: it was structurally incapable of reporting anything else. Replaying a genuinely failed deployment through the new judge returns `failed` while its container still reports `running:healthy`, and its build log ends on `Deployment failed. Removing the new version of your application.` — the evidence that was previously unreachable.

Two facts the OpenAPI document gets wrong, both confirmed live and both silent failures if trusted: `/deployments/applications/{uuid}` returns `{ count, deployments }`, not the bare array of `Application` it documents, so the client unwraps the envelope; and deployment log entries carry `{ command, output, type, timestamp, hidden, batch }` with no sequence field, so the array's own order is preserved rather than sorted on a key that does not exist. Note also that `running:unknown` — a container with no healthcheck, about half the applications on that instance — is a healthy outcome, not a suspicious one: where there is no healthcheck there is nothing to fail.

Consequences for the UI, all of which were previously impossible: a failed deploy raises an error toast instead of silently clearing; the "queued" toast is styled as information rather than success, because acceptance is not completion; the Redeploy-needed chip (ADR-0005) now survives a failed deploy, which makes its stated meaning — "config saved but not applied" — true for the first time; and the logs viewer can show the deployment's own build output, which is the only place a failed build explains itself.
