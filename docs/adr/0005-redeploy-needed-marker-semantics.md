# 0005 Redeploy-needed marker is client-derived and clears asymmetrically per build pack

The Details tab lets a user edit an Application's Docker image tag (dockerimage) or git branch (git-based) and saves it immediately via `PATCH /applications/{uuid}`. A saved change is not live until the container is recreated, so the row shows a Redeploy-needed chip until then.

The marker is **derived client-side**, not persisted: a page-level set of resource uuids is raised when the PATCH succeeds and cleared when a pending action converges. Coolify exposes no "what the running container was last started with" field, so we deliberately do not try to diff against deployment snapshots.

Clearing is **asymmetric by build pack** because Coolify treats Restart differently per type (verified in `ApplicationDeploymentJob`): the constructor forces `restart_only = false` for `dockerimage` and `dockerfile` apps, so a Restart on a dockerimage app re-resolves the *updated* tag and recreates the container — it genuinely applies the change. For git-based apps, `restart_only` stays true and `just_restart()` restarts the existing image at the current commit; a changed branch is **not** applied. So: a converging **Redeploy clears for all app types**; a converging **Restart clears only for dockerimage apps**. A failed or errored deploy never clears, and there is deliberately **no manual dismiss** — the marker means "we have not seen this config applied," and letting the user clear it would let it lie (the cost of a stale marker after an out-of-band deploy is low and self-corrects on the next deploy here).
