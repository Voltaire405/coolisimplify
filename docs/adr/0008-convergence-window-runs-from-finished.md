# 0008 The Convergence Window runs from `finished`, not from dispatch

ADR-0006 stopped the app reporting broken deploys as successful. It then reported working ones as failed — the same defect mirrored, and the more visible of the two, because the deploy the user was watching succeed raised an error toast while it did.

The verdict for an Application is authoritative once `GET /deployments/{uuid}` reads `finished`, but `finished` describes the *build*, not the container it produced: a build that completes onto a container that immediately exits is a broken deploy, so the container still had to be checked. It was checked behind a grace window — and the window was measured with `elapsedMs`, which counts from the moment the action was **dispatched**.

That reference point makes the window worthless. The build owns nearly all of the elapsed time; by the time it ends, a 90-second build has spent an 8-second window eleven times over. So the window was open only for deploys that finished in under 8 seconds — of which there are none — and for every real one the first poll after `finished` landed on a container Coolify had just replaced, which spends its opening seconds `starting` and then failing a healthcheck that has not had time to pass. Both read as "not `running` and healthy", and the judge went straight to `failed`. Nothing was wrong except the clock the window was read from.

The window now starts when the deployment is *first observed* `finished`, passed to the judge as `sinceFinishedMs`, and it is `POST_DEPLOY_GRACE_MS` = 60 s rather than 8 s: 8 s is the scale of a stale refetch, while what is actually being waited on is a container boot and a Docker healthcheck `start_period`, commonly 30–60 s. The stamp is taken once — `finished` is terminal, so re-stamping each poll would slide the window forward and it would never close.

A second rule follows, and it is the one ADR-0006 already argued in the other direction: **only positive evidence counts, for failure as much as for success.** Past the window, a container that is `exited` or `error` is a failed deploy — that is evidence. A container still `starting`, `restarting`, or still unhealthy is not evidence of anything; it is an unfinished story. Those keep waiting and the caller ends in `timeout`, reported as an unknown outcome, which is what ADR-0006 already established that giving up means. The window bounds how long a failure may take to *establish*; it does not manufacture one. Success is unaffected and still resolves on the first poll that sees a healthy container, so the common case gets no slower.

The fix had to be applied twice, because there were still two call sites. ADR-0006 extracted the batch loop into `lib/wait-for-completion.ts`, but `app/page.tsx` kept a resolver `useEffect` for single actions calling `judgeAction` directly — the surviving half of the duplication that let the original defect through, and it carried this one identically. That is two defects in a row landing in both copies, so the second half was collapsed onto the first rather than left for a third.

`executeAction` now awaits `waitForCompletion` instead of registering state for an effect to adjudicate. The resolver effect and the deployment-polling effect are both gone: the waiter does its own polling, including the periodic listing refetch — re-reading the listing is *how* it observes the container, so the row pill stays current for free. `PendingAction` collapses to `Map<uuid, action>`, holding only what the pill and the busy guard read; the deployment handle is a local in the dispatch, the timeouts belong to `timeoutFor`, and the verdict belongs to the judge. `page.tsx` no longer imports `judgeAction` at all.

What survives per-path is only what genuinely differs: single actions raise a toast, the queue marks the item failed. Everything else settles through one shared `settleAction` — which closed a bug in passing. Clearing the Redeploy-needed chip lived in the resolver, and the resolver never saw queue items, so a redeploy run from the **Batch Queue** left the chip standing even when it succeeded, contradicting what ADR-0005 says the chip means. Both paths now settle identically.

`page.tsx` has no test seam — it is a component, and components are deliberately outside the coverage scope (ADR-0007). Every rule moved out of it is a rule that became reachable from a spec; what remains there is dispatch and presentation.

What made this survivable in the first place was a test suite that could not see it. Every spec held the container at `running:healthy` for the entire run, so the container was never once observed mid-boot — the exact state the bug is about. `lib/wait-for-completion.test.ts` now drives a 90-second build whose container is replaced when it ends, in both shapes (`starting` and `running:unhealthy`), alongside the same timeline ending in `exited (1)` to prove the window delays a real failure rather than waiving it.
